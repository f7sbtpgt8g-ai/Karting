# Karting Telemetry Analysis Tool

A local data analysis tool for kart racing telemetry exported from a
**Unipro laptimer** (TSV format). Loads one or more session files, segments
the track into corners from the GPS trace, and produces a ranked
**"Top 3 areas to focus on"** report -- with a plain-language coaching note
per segment -- plus a kart-setup input form and a correlation engine that
suggests concrete setup changes from telemetry patterns.

Built for a Rotax Senior EVO junior driver on Danish/Scandinavian tracks,
but the analysis core is track/class-agnostic; only the setup-suggestion
defaults (peak-power RPM band, carb model) lean Rotax EVO.

## Status

Originally built against a written spec only (the sample export it referenced
wasn't actually available in that environment), then validated against a
real 82MB / ~898,000-row / 11-session Unipro export from an actual track day.
That validation pass surfaced and fixed several real-world quirks the
original spec's single sample file didn't cover -- see below. The synthetic
fixture (`tests/fixtures/synthetic_session.tsv`, generated by
`tests/generate_fixture.py`) still backs the automated test suite, since a
real export isn't checked into the repo, but the parser and analysis
pipeline have now both been exercised end-to-end against real telemetry.

**Real-world quirks found during that validation, beyond the original spec:**
- **GPS-derived channels don't all necessarily fire on the same row.** The
  spec's original sample export had `Heading`/`GPS Speed`/lat-lon/G-forces
  all update together as one atomic GPS fix. A real export instead had two
  *independent* groups: position (`Heading`, `Latitude`, `Longitude`, DOPs,
  `Altitude`) fires together, but `GPS Speed` and the three G-force channels
  fire on their own separate cadence that never once shared a row with the
  position fix in that file. `telemetry/parser.py` now distinguishes
  `GPS_FIX_COLUMNS` (position group) from `GPS_MOTION_COLUMNS` (speed/G-force
  group), and `corners.py::lap_gps_trace` aligns each independently via
  `merge_asof` rather than assuming they share rows. Getting this wrong
  silently produced all-NaN speed and G-force data, which in turn produced
  empty braking-zone detection and washed-out G-G diagrams -- worth knowing
  if those look empty on a new export.
- **A `GPS Speed`-truly-absent fallback still exists as a backstop**
  (`corners.py::_derive_speed_from_distance`): if `GPS Speed` really isn't
  populated anywhere (rather than just being on a different cadence, as
  above), speed is derived from `GPS Distance`'s rate of change instead, and
  flagged via a `gps_speed_is_estimate` column / a banner in the app.
- **A given export's header can include extra undocumented columns** (one
  real file had both `Inverse Corner Radius` and a separate `Corner Radius`
  column not in the original spec). The parser only requires its known
  columns to be *present*; unrecognized extra columns are harmless and
  ignored.
- **Session-restart detection needs a real threshold, not any backward time
  step.** Row order within a session can jitter by milliseconds (different
  channels are buffered/flushed independently); the original implementation
  treated any backward step as a new session, which silently fragmented one
  real session into dozens of spurious pieces. Fixed to require a large drop
  (>1s) that lands back near zero -- see `telemetry/parser.py::split_sessions`.
- **Lap segmentation must follow contiguous runs of `Lap Number`, not group
  by its raw value.** Grouping by value silently merges two physically
  distinct laps whenever a lap number repeats non-adjacently (a missed
  session-restart split, or a stray mistimed reading) -- this was the cause
  of a reported "59s lap that doesn't match the dash" bug. Fixed in
  `telemetry/laps.py::lap_table`.

If you hit a *different* real-world quirk on your own export, the parser
generally fails loudly (missing expected column) rather than silently
misinterpreting data -- but channel-level surprises like the ones above
(a column present in the header yet structured differently than assumed)
won't necessarily raise an error, so a sanity check against a new device/
firmware/config is still worthwhile (see "Validating against a real export").

## Quirks of the Unipro TSV export (read this before touching the parser)

- **Header row**: 28 quoted, tab-separated column names (see
  `telemetry/parser.py::COLUMNS` for the exact list and order).
- **Decimal separator is a period**, not a comma, despite Unipro being a
  Danish company.
- **Every row is a sparse, asynchronous sensor event, not a full sample.**
  Each channel logs at its own native rate and appends a new row with only
  that channel (plus `Start Date`/`Start Time`/`Lap Number`/`Session
  Time`/`Lap Time`, which are always populated) filled in -- every other
  column is blank on that row. There is no fixed sample rate. Do **not**
  read rows as if each one were a complete sample; use
  `Session.extract_channel()` / `Session.align_channels()` to reconstruct
  per-channel time series and align them only where a calculation actually
  needs multiple channels together.
- **`Session Time` and `Lap Time` are in nanoseconds.** Both are divided by
  1e9 on load (`session_time_s` / `lap_time_s` columns).
- **`Lap Time` is the authoritative per-lap clock.** Lap boundaries come
  directly from `Lap Number` increments -- they are not re-derived from GPS
  start/finish crossings.
- **A single TSV file can contain more than one session/run.** If the
  logger was stopped and restarted, `Lap Number` and `Session Time` both
  reset to 0 partway through the file. The parser detects this (a drop in
  `Session Time`) and splits the file into separate `Session` objects
  automatically -- see `telemetry/parser.py::split_sessions`.
- **No sector timing exists in the data.** Corners/straights are detected
  generically from the GPS trace (heading-derived curvature, or
  `Inverse Corner Radius` directly when a given export has it populated) --
  see `telemetry/corners.py`.
- **No track name, throttle, brake, gear, or EGT/lambda channel exists** in
  the confirmed export. Braking zones, power-on phases, and jetting
  diagnostics are all *inferred* from RPM and GPS-derived G-forces, and are
  labeled as estimates throughout the code and UI -- never presented as
  direct measurements.

## Project layout

```
telemetry/            Parsing + analysis core (independently testable, no UI code)
  parser.py            TSV ingestion, session splitting, sparse-channel reconstruction
  laps.py               Lap segmentation, outlier/anomaly detection, consistency
  corners.py            GPS-based corner/straight segmentation
  metrics.py             Speed/RPM/G traces, braking & throttle inference, GG diagram
  delta.py                Theoretical best lap, delta-time-vs-distance trace
  focus_areas.py           Top-3 focus area scoring + coaching notes
  setup_config.py           Kart setup schema (YAML-backed)
  setup_engine.py             Setup correlation / suggestion engine
  comparison.py                 Reference-lap diff, progression, driver comparison
  storage.py                     SQLite session library (for the "history" feature)
app.py                Streamlit UI (thin orchestration layer over telemetry/*)
scripts/ingest.py     CLI ingestion into the session library (automation-friendly)
tests/                pytest suite + synthetic fixture generator
config/               Example kart setup YAML
```

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate

```

## Running the app

```bash
source .venv/bin/activate
streamlit run app.py
```

Then open the local URL Streamlit prints, and upload one or more `.tsv`
exports in the sidebar. You'll be asked for your kart setup right after
upload (skippable) -- if it points to a medium/high-confidence gearing,
jetting, tyre-pressure, or chassis-balance issue, that gets folded straight
into the **Top 3 Focus Areas** headline alongside the usual corner-based
time-loss items, rather than sitting only in the separate setup tab. That
headline is the landing view, in plain language, before the deeper
technical charts (speed/RPM/delta traces with a linked track-map position
marker, G-G diagram, track map, braking zones, per-corner entry/apex/exit
speed & RPM, peak-power RPM zone time, consistency, progression).

## Exporting the correct TSV from Unipro Analyser

1. Open your session log in Unipro Analyser.
2. Use the software's TSV/text export for the full data log (not a summary
   or lap-times-only export) -- you want the raw channel log with all 28
   columns listed above.
3. Save with a `.tsv` extension. Decimal points, not commas, should be used
   for numeric values (this is the Analyser default; don't change locale
   settings).
4. If a session was stopped and restarted during the same export (e.g. two
   heats on one file), that's fine -- the tool detects and splits multiple
   sessions automatically.

## Filling in the kart setup

You're prompted for gearing, carburettor, tyre, and chassis settings, plus
track/session context and the engine's peak-power RPM band, right after
uploading a file (none of this exists in the TSV, so it's all
user-supplied) -- skip it if you just want to look at telemetry first, and
fill it in later from the **Kart Setup** tab, which has the same form.
Download it as YAML to keep a record; see `config/setup_example.yaml` for
the file format, or load/save it directly via `telemetry.setup_config.KartSetup`.

The setup correlation engine (also in that tab) cross-references your
stated setup against telemetry patterns -- e.g. peak RPM on the longest
straight vs. your stated peak-power band, RPM hesitation during power-on as
a jetting proxy, lateral-G trend across the session as a tyre-pressure
proxy, left/right corner-speed asymmetry as a chassis-balance proxy.
Medium/high-confidence results here also compete for a slot in the Top 3
Focus Areas headline (see `telemetry/focus_areas.py::blended_top_recommendations`).

**Every suggestion is labeled with a confidence level and phrased as a
hypothesis to test, never a certainty** -- there's no EGT/lambda, throttle,
or brake channel in this export, so these are inferences from lap data, not
direct sensor confirmation. Low-confidence jetting suggestions in
particular should be verified with a plug chop before changing anything.
Gearing direction matters here: for a direct-drive kart, engine RPM = axle
RPM × (rear teeth / front teeth), so *lowering* RPM at a given speed means
*lowering* that ratio (fewer rear teeth or more front teeth) -- the
suggestion text spells out the specific tooth-count direction rather than
just "gear up/down" to avoid ambiguity.

## Interpreting the outputs

- **Top 3 Focus Areas**: the segments (corners or straights) where you have
  the most time to gain vs. your own theoretical best lap (sum of your best
  observed time in each segment across the session's clean laps), each with
  a diagnosed likely cause (braking point, minimum corner speed, exit RPM,
  line consistency) where the data supports one -- blended with any
  medium/high-confidence kart setup hypothesis, which is guaranteed a slot
  ahead of marginal corner items since a setup mismatch affects the whole
  session rather than one corner.
- **Speed, RPM & delta trace** (Speed & Delta tab): stacked, distance-aligned
  charts for each selected lap, plus a track map alongside with a slider
  that moves a position marker along the chosen lap's GPS path -- drag it to
  see exactly where on the circuit a given point in the charts corresponds
  to. The delta panel is continuous time gained/lost vs. a reference lap;
  positive = slower than the reference at that point, negative = faster, and
  it's the single most direct view for pinpointing exactly where time is
  lost.
- **G-G diagram**: lateral vs. longitudinal G for one lap. Points farther
  from the origin use more of the available grip.
- **Braking zones / RPM trace / per-corner entry-apex-exit table**: labeled
  as *inferred* where relevant -- there's no direct brake or throttle
  channel, so braking zones come from deceleration patterns. The RPM trace
  shades the peak-power band, and the per-corner table breaks out speed and
  RPM at each corner's entry, apex (minimum-speed point), and exit.
- **Time in peak-power RPM zone**: what fraction of a lap is spent with RPM
  inside the stated peak-power band, per lap and as a session-wide chart --
  a quick read on whether gearing is keeping the engine on the boil.
- **Outlier laps**: out-laps, in-laps, and statistical outliers (e.g. a spin
  or a stoppage) are flagged and excluded from best/average stats, but stay
  visible in the lap table for review.

## Validating against a real export

Once you have a real Unipro TSV:

```bash
source .venv/bin/activate
python -c "
from telemetry.parser import load_sessions
sessions = load_sessions('path/to/your_export.tsv')
for s in sessions:
    print(s.session_id, len(s.df), s.df['Lap Number'].nunique())
"
```

If that runs without error and the lap counts look right, load the file
into the Streamlit app and check the lap time table and RPM/speed ranges
look plausible for your class before trusting the deeper analysis.

## Running the tests

```bash
source .venv/bin/activate
python -m pytest
```

The suite runs against `tests/fixtures/synthetic_session.tsv`, a fixture
generated by `tests/generate_fixture.py` from a simulated oval track. It
reproduces the confirmed structural quirks (sparse single-channel rows,
nanosecond time, mid-file session reset, an injected "spin" lap ~3.7x the
median lap time) so the parser and analysis modules are exercised
end-to-end. Regenerate it with:

```bash
PYTHONPATH=. python tests/generate_fixture.py
```

## Session library (history) & automation

`telemetry/storage.py` persists parsed sessions to a local SQLite database
(lap summaries + a pickled cache of each session's raw dataframe) so trend
views don't require re-uploading every file. Ingest files from the command
line -- e.g. from a script triggered after a race-day upload -- with:

```bash
python scripts/ingest.py session1.tsv session2.tsv \
    --driver "Your Name" --track "Track Name" --session-type practice \
    --db data/sessions.db
```

## Known limitations / not yet implemented

- PDF export is not implemented; the exportable summary is HTML-based
  (Plotly figures export cleanly to standalone HTML).
- Ideal-line overlay and fuel/tyre-effect isolation described in the
  original spec's "additional features" section are not built yet --
  the delta-time trace and consistency trend cover most of the same ground
  today.
- Corner detection thresholds (`telemetry/corners.py`) are reasonable
  defaults tuned against the synthetic fixture; they may need adjustment
  for a real track's actual corner geometry and GPS noise characteristics.
